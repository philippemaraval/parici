Vérifier une restauration

Le workflow PostgreSQL backup produit une archive chiffrée, contrôle son empreinte, la restaure dans PostgreSQL isolé puis conserve l’archive. L’administration affiche le résultat réel de ces trois étapes.

  1. Dans le workflow, choisir une exécution réussie puis télécharger l’archive .dump.enc et son fichier .sha256.
  2. Préparer une base PostgreSQL locale vide, distincte de la base source. Utiliser une version du client PostgreSQL compatible avec celle du serveur.
  3. Configurer les variables ci-dessous dans un terminal sécurisé, puis exécuter le script. La phrase de chiffrement reste dans l’environnement et ne doit pas être ajoutée à un fichier suivi par Git.
  4. Contrôler les comptes, contenus et progressions dans l’environnement isolé. Le simple succès SQL ne prouve pas le bon fonctionnement de tous les parcours du jeu.
CAMINO_RESTORE_ISOLATED=1
RESTORE_DATABASE_URL=postgresql://…@localhost:5432/camino_restore
BACKUP_ENCRYPTION_PASSPHRASE=…
# Exporter ces variables sans conserver les secrets dans l’historique.
bash scripts/postgres_restore_test.sh chemin/camino.dump.enc

Le script refuse une destination distante et une base identique à la source. Il ne restaure jamais automatiquement la production. Une restauration de production exige une procédure séparée : arrêt des écritures, sauvegarde de l’état courant, périmètre précis et vérification métier.

Sans exécution réussie, l’administration indique « aucune preuve enregistrée ». Un workflow empêché de démarrer par GitHub ne produit pas de nouveau résultat en base.
